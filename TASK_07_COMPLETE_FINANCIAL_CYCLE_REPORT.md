## Cashbox Architecture

Cashboxes are real rows with an explicit currency and warehouse scope — `box-usd` and `box-syp` are gone. Each warehouse has one default cashbox per currency, so a normal sale needs no extra clicks; an authorised user may still pick another allowed box. The migration provisioned a default USD and SYP cashbox for every existing warehouse with a zero opening balance, which is configuration rather than invented money.

**Balances are never stored.** A cashbox balance is `opening_balance + Σ inflows − Σ outflows` over its complete movement history, so a balance cannot drift from the documents that justify it. Cancellations add compensating movements rather than removing old ones, which is why movements are counted regardless of voucher status.

## Voucher Architecture

Every voucher carries `source_type` (`manual`, `sale`, `purchase`, `sales_return`, `purchase_return`, `cashbox_transfer`, `expense`), the source document id and number, and — for automatic vouchers — the exact payment row it came from. Numbering is `RCV-YYYY-NNN`, `PAY-YYYY-NNN`, `EXP-YYYY-NNN` and `TRF-YYYY-NNN`, allocated from database sequence tables.

Both notes are preserved separately: the system-generated `system_note` and the user's own `user_note`.

## Automatic Voucher Generation

Posting a document writes its financial effect in the **same transaction**:

| Document | Cash actually moved | Result |
| --- | --- | --- |
| Sale | customer paid | **Receipt voucher** + inflow — `قبض آلي عن فاتورة بيع INV-2026-015` |
| Purchase | shop paid | **Payment voucher** + outflow — `صرف آلي عن فاتورة شراء PUR-2026-008` |
| Sales return | refunded to customer | **Payment voucher** + outflow — `رد مبلغ للعميل عن مرتجع RET-2026-004` |
| Purchase return | recovered from supplier | **Receipt voucher** + inflow — `قبض من المورد عن مرتجع مشتريات RET-2026-009` |

No user re-entry is required for a payment the invoice already knows about. When no money moves, no voucher and no cash movement are created.

## Invoice → Finance Flow

```
Sale $1,000 paid $1,000 →  invoice + payment fact + RCV-2026-018 + cashbox inflow $1,000
                           + ledger debit $1,000 (sale) + ledger credit $1,000 (receipt) → receivable 0
Sale $1,000 paid $0     →  invoice only. No voucher, no cash movement, receivable $1,000
Sale $1,000 paid $300   →  invoice + RCV + inflow $300, receivable $700
```

Every record — voucher, movement and ledger entry — carries the invoice id and number, so a manager can trace an invoice into Finance and a voucher back to its invoice.

## Customer Receivables and Supplier Payables

No editable balance field is mutated; the immutable opening balance stays separate. The subledger holds a signed net where positive means the partner owes the shop:

```
customer outstanding = opening_balance + Σ(debit − credit)
supplier payable     = opening_balance − Σ(debit − credit)
```

Sales debit, receipts credit, sales returns credit, purchases credit, payments debit, purchase returns debit. This reproduces the Task 04 and Task 05 outstanding figures exactly while now also including vouchers and returns, and it works for a partner that is both customer and supplier.

## Currency Handling

Each paid currency produces its **own** voucher, movement and cashbox entry. A $400 + 1,300,000 SYP sale stores 1,300,000 SYP with rate 6,500 and its $200 equivalent — the original amount and currency are never replaced by the converted value, and a historical record is never re-valued at today's rate.

## Payment Allocation

`voucher_allocations` records a receipt or payment applied against one or several invoices (`RCV → INV-001 $400, INV-002 $600`). Over-allocating beyond the voucher amount is rejected. Allocation is optional: a manual receipt may simply reduce the partner's overall balance.

## Cash Movements

Every movement records cashbox, direction, amount, currency, rate, USD equivalent, voucher, source invoice or return, partner, warehouse, actor, timestamp and description. The Finance journal screen is now this ledger.

## Returns Financial Effect

A sales return credits the customer for the whole return value; cash actually handed back is a payment that settles part of that credit, so a $2,970 return refunded $100 in cash reduces the receivable by $2,870 and takes $100 out of the box. A credit-only return moves no cash at all. A purchase return debits the supplier; cash recovered is a receipt. Gold and scrap exchange remains the explicit Task 06 settlement boundary — **no cash movement is fabricated for gold**.

## Cancellation and Reversal

Nothing is hard-deleted. Cancelling a manual voucher marks it `cancelled` and writes an equal, opposite voucher with its own compensating movement; both remain visible. Cancelling a sale, purchase or return reverses every voucher that document posted the same way. Automatic vouchers cannot be cancelled on their own — the source document must be cancelled, which keeps finance and the document in step.

## Partner Account Statement

`GET /api/v1/finance/partners/:id/statement` returns the opening balance, then every invoice, automatic voucher, manual voucher, return and reversal with date, document type, document number, description, currency, original amount, debit, credit and running balance, ending in the closing balance. The print modal that previously said no movements could be shown now renders this table. No legacy localStorage transaction is mixed in.

## Idempotency

A partial unique index on `(source_type, source_payment_id)` makes it structurally impossible for one payment fact to produce two automatic vouchers. Manual vouchers and transfers use UUID idempotency keys, so a double-click or retry returns the original document. Verified: `1 sale → exactly 1 receipt voucher`, and a repeated manual submit returns the same voucher id.

## Atomicity

Invoice, payments, inventory, automatic vouchers, cash movements, subledger entries and audit all commit together or roll back together. If a required cashbox is missing, posting fails with a clear message and the invoice does **not** post — an invoice is never left claiming money moved into a box that does not exist.

## Remaining Risks

1. **Opening cashbox balances are zero.** The demo balances were removed as required and the new production cashboxes start empty, so USD cash currently reflects only movements since the deploy. Real opening balances should be entered once — cashbox creation supports an opening balance, or the existing boxes can be updated.
2. **Vouchers may drive a cashbox negative.** Only transfers refuse to overdraw. A hard guard on every payment would have blocked legitimate work while opening balances are still zero. Worth enabling once real balances are entered.
3. **Posted vouchers cannot be edited.** The old screen offered "تعديل"; it now reports that posted vouchers are corrected by cancellation plus a new voucher. That is deliberate immutability, but it is a behaviour change for the user.
4. **Allocation is recorded, not enforced.** Allocations are stored and capped at the voucher amount, but an invoice-by-invoice settled/unsettled status is not yet derived from them.
5. **Gold and scrap settlement remains outside cash.** Unchanged from Task 06 and explicitly preserved for the future Gold Weight Accounts work.
6. **No general ledger or chart of accounts**, by design for this task.
7. **Dashboard, Reports and Shifts still read legacy local state** and do not yet consume the finance subledger. They are out of Task 07 scope.
8. **The local development database holds duplicate warehouses** from repeated seeding (no unique index on warehouse name), which produced duplicate default cashboxes there. Production has one warehouse and exactly two cashboxes; the dev seed is worth hardening separately.
