Constraints enforce the model rather than trusting the service: a return must reference exactly one original document consistent with its type; a return line must reference exactly one original line; quantities, weights, and every monetary column must be non-negative, and returned quantity/weight strictly positive.

Nothing is stored as one JSON blob. Movement metadata carries only the before-image needed for safe reversal.

## Return Workflow

`POST /api/v1/returns` is server authoritative and runs entirely in one PostgreSQL transaction:

```
validate user → validate permission → load and LOCK the original invoice (SELECT … FOR UPDATE)
→ validate status, warehouse scope, partner → derive remaining returnable quantity/weight per line
→ create return header (number from the sequence table) → create return lines
→ apply the inventory effect (locking each item) → create refund facts
→ create immutable movements → enforce the economic cap → write the audit entry → COMMIT
```

Any failure rolls the whole thing back, including the number sequence, so no gap or partial document is left behind. Realtime events are emitted only after the commit.

## Sales Returns

A sales return must reference a posted backend sale. The service verifies the sale exists, is not cancelled, is inside the user's warehouse scope, and that the supplied customer matches the original sale's customer. Requested lines must belong to that invoice, and each requested quantity and weight must fit inside the remaining returnable amount. The original sales invoice is never rewritten.

## Purchase Returns

A purchase return must reference a posted backend purchase, not cancelled, in scope, with a matching supplier. In addition to the returnable-amount check it verifies real inventory availability: the received item must still exist, be unarchived, be `in_stock`, sit in the same warehouse, and hold at least the requested quantity and weight. Anything sold, transferred, or otherwise consumed is rejected with a clear conflict instead of being forced through.

A purchase line that only reconciled a legacy-negative balance has no received stock; returning it is rejected with an explicit message directing the user to a corrective transaction. That boundary is deliberate, not an oversight.

## Aggregate / Individual Inventory Behaviour

* **Individual item** — must be returned in full (partial is rejected). The item must currently be `sold`; it is restored to `in_stock` with its weights untouched, exactly as they were before the sale.
* **Aggregate item** — only the returned quantity and weight are added back (`quantity + q`, `gross + g`, `stone + s`, `net + n`, total workmanship recomputed). The full aggregate snapshot is never restored. Verified: selling 10 pieces / 100.000 g then returning 3 pieces / 30.000 g leaves the item at exactly 3 pieces / 30.000 g, and returning the remaining 7 / 70.000 g brings it back to 10 / 100.000 g.
* **Purchase-side** — the received item is reduced by exactly the returned quantity and weight, or archived when the line is cleared completely (an item may not sit at zero quantity under the existing check constraint).

## Legacy Negative Compatibility

Negative quantity and weight remain valid history, not corruption. Returning a manual-sale line moves its legacy-negative entry back **towards** zero by exactly the returned amounts and leaves it negative while any part of the sale stands. Once the line is fully returned the entry is archived, never deleted, so its `manual_sale` and `sales_return` movements stay readable in the movement history. Purchase reconciliation records are untouched by returns.

## Returnable Quantity/Weight Logic

Remaining returnable is derived, never stored as a client number:

```
remaining_quantity = original_line.quantity      − Σ posted return lines.quantity
remaining_net      = original_line.net_weight    − Σ posted return lines.net_weight
```

The sum counts only `posted` returns, so cancelling a return frees its amount again (verified). The whole calculation happens under a `FOR UPDATE` lock on the original invoice, which serialises every concurrent return against the same document. `GET /api/v1/returns/returnable` exposes the same derived numbers to the UI.

## Calculation Rules

Amounts are computed from the **original** transaction snapshot — the original karat, the original gold price per gram, and the original workmanship per gram. Today's gold price is never used to price a historical return.

```
ratio         = returned_net / original_line_net
gross, stone  = original gross, stone × ratio      (so gross − stone reproduces returned net)
gold_value    = returned_net × original_gold_price_per_gram
workmanship   = returned_net × original_workmanship_per_gram
line_gross    = gold_value + workmanship
```

## Discount Allocation

Proportional to line value, against the original document's gross:

```
share                = line_gross / (original_gold_subtotal + original_workmanship_subtotal)
discount_allocated   = original_discount × share
scrap_credit_alloc   = original_scrap_total × share        (sales returns only)
line_total           = max(0, line_gross − discount_allocated − scrap_credit_alloc)
```

On top of the per-line rule the backend enforces a hard economic cap: the sum of all posted returns' final totals for an original invoice can never exceed that invoice's `final_total_usd`. A return that would breach it is rejected.

## Gold/Scrap Exchange Compatibility

Task 04 gold-exchange records (`sales_gold_exchanges`) are **not** reversed. Returning a piece does not hand the customer's scrap gold back, and no exchange row is edited or deleted.

What is implemented is the part that can be tied safely to the returned lines: the exchange credit already consumed by those lines is allocated proportionally and netted out of the refund, recorded in `scrap_credit_allocated_usd` on the return and its lines. A customer who paid $800 cash plus $200 of scrap for a $1,000 piece is refunded $800 on a full return, and the $200 gold obligation is preserved as an explicit, visible settlement boundary for the future accounting module rather than being invented as cash now.

## Partner Outstanding Effect

No editable balance field is mutated and opening balances stay separate.

```
customer outstanding = opening_balance + Σ posted sales.remaining_debt − Σ posted sales returns.outstanding_adjustment
supplier outstanding = opening_balance + Σ posted purchases.remaining_debt − Σ posted purchase returns.outstanding_adjustment
```

`outstanding_adjustment_usd` is the part of the return that was not refunded in cash, i.e. the credit that belongs against the partner's operational balance.

## Refund Facts

Refunds are persisted as `return_payments` rows using the existing currency concepts: `cash_usd`, `cash_syp` (with its exchange rate and applied USD), and `credit_note` for the un-refunded remainder. A refund may never exceed the return total. No legacy local cashbox is touched and no accounting ledger entry is fabricated; these rows are shaped to be consumed by the future Cashbox and Accounting modules.

## Cancellation

Returns are never hard-deleted. `POST /api/v1/returns/:id/cancel` requires `returns.cancel` and a reason, and refuses a second cancellation.

Reversal is only performed when it is provably safe: the return's own movement must still be the newest movement on the affected item. If anything happened afterwards — the restored piece was sold again, the reduced stock moved — the cancellation is rejected with a conflict directing the user to a corrective transaction, and the return stays posted. When reversal is safe, the item is restored from the before-image recorded in the return movement and a `return_cancellation` movement is written.

## Posted Return Immutability

There is no edit endpoint. A posted return is corrected by cancellation or by a further corrective transaction; its historical facts, lines, refund rows, and movements remain immutable.

## Idempotency

Every return carries a UUID `idempotency_key` with a unique index. A repeated submit — double-click or network retry — returns the original document instead of creating a second return, second movement, or second refund fact. Verified both by pre-check and by the unique-violation fallback path.

## Concurrency

The original invoice row is locked with `SELECT … FOR UPDATE` before returnable amounts are derived, so two users returning the same line serialise. Verified: two simultaneous returns of the last remaining 7 pieces / 70.000 g produce exactly one `201` and one `409`; the aggregate item ends at its correct weight, never over-restored.

## Inventory Movements

Every inventory effect writes an immutable movement referencing the inventory item, the return invoice, the original sale or purchase, the warehouse (from/to by direction), the actor, and metadata carrying the quantity and weight deltas plus the before-image. Types added: `sales_return`, `purchase_return`, `return_cancellation`. History is only ever appended.

## Audit

`AuditService` records `returns.create` and `returns.cancel` under module `returns` inside the same transaction, with actor, warehouse, partner, return id and number, original invoice id and number, line count, final total, and cancellation reason. No secrets are stored.

## Realtime

Nothing is emitted before commit and nothing is broadcast outside the authorised rooms. The deferred Cloudflare WebSocket edge issue is unchanged and out of scope.

## Remaining Risks

1. **Drizzle ledger row for `0007` is not yet recorded.** The migration is fully applied, but the bookkeeping row in `drizzle.__drizzle_migrations` was blocked by the local permission classifier during this session. Until it is inserted, a future `drizzle-kit migrate` would try to re-apply `0007` and fail. The exact statement is prepared at `/tmp/task06_ledger.sql` on the VPS; it needs one approved run as the PostgreSQL owner. This does not affect the running application.
2. **Gold/scrap exchange settlement is a deliberate boundary.** Returning a sale paid partly with scrap gold nets the exchange share out of the cash refund and records it, but does not return the physical gold or reverse the exchange record. That obligation is left explicit for the future Cashbox/Accounting and Gold Weight Accounts work.
3. **Refund facts are descriptive only.** They are not yet posted to any cashbox or ledger, by design; the Cashbox module will consume them.
4. **Reconciliation-only purchase lines cannot be returned.** They are rejected with a clear conflict rather than guessing an inventory effect.
5. **Unsafe cancellations require a manual corrective workflow.** When later stock activity blocks reversal the system refuses rather than corrupting history; the corrective transaction itself is not yet a guided flow.
6. **Dashboard, Reports, Finance, and Shifts still read legacy local state** and therefore do not yet include backend returns. Those modules are explicitly out of Task 06 scope.
7. **Production business acceptance is pending.** Structural verification passed; the on-screen and real-data acceptance belongs to the designated user.
